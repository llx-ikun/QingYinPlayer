# v2.1.9 · 导入即复制：把「引用路径」改成「受管理曲库」

## 问题

v2.1.8 及以前，导入只做了一件事：把**原文件的绝对路径**写进 `data.json`。
后果是曲目和文件位置强绑定 —— 用户把歌挪个文件夹、或清空下载目录，列表里就出现
一堆「失效」，必须重新导入。

你的要求「导入音乐是把文件复制到软件里」，本质是要求**把引用改成归属**：
导入完成后，文件归软件管，原文件动与不动都不影响播放。

## 决策

| 选项 | 说明 | 取舍 |
|---|---|---|
| A. 维持引用（旧） | 只记路径 | 省空间；但文件一动就失效 |
| **B. 复制进曲库（采用）** | 导入时复制到 `%APPDATA%/轻音播放器/library/` | 与源文件解耦、可移动可清理；**代价是占双份磁盘** |
| C. 移动进曲库 | 导入时剪切 | 省空间；但会「偷走」用户原文件，风险高、不可逆 |

选 B：可逆、可解释，符合「导入」的一般直觉（和网易云/QQ 音乐一致）。

## 具体实现

### 新增 `app/library.py`

- `file_signature(path)`：**文件大小 + 首尾各 64KB 的 blake2b**。
  为什么不做整文件哈希 —— 视频动辄几百 MB，整文件哈希会让导入变慢；size+两端
  已足够区分正常媒体文件。
- `import_into_library(src, library_dir) -> (目标路径, 是否复制)`：
  - 目标已存在且**内容相同** → 复用（重复导入不占第二份空间）
  - 目标同名但**内容不同** → 文件名追加 8 位指纹后缀，不覆盖
  - **同名 `.lrc` 一并复制**（自动歌词按「音频主干.lrc」同目录查找，不带上就失效；
    这是全量回归抓到的真实回归 —— 一开始只复制了媒体文件，歌词测试就红了）
  - 写 `.part` 临时文件再 `os.replace` 原子落盘，失败不留半成品
- `is_in_library(path, library_dir)`：判断某曲目是不是软件自己的副本
- `safe_stem()`：过滤 Windows 非法字符 `< > : " / \ | ? *`

### `app/scanner.py`

`ScannerWorker` 增加可选 `library_dir`：
- 传了就**先复制、再从副本读元数据**，`track.path` 指向曲库副本；
- 复制失败（磁盘满 / 无权限 / 源文件被移走）→ 跳过该文件并计数，不中断其余文件；
- 不传则维持旧语义（单测和外部脚本按老方式调用）。

### `ui/main_window.py`

- `_start_import` 传 `library_dir()`，完成提示改为「已复制到曲库（M 个失败已跳过）」
- `_remove_from_library`：曲库内的副本在移出时一并删除；老条目（外部路径）仍按
  「不动磁盘文件」处理，对话框文案自动区分

## 已知取舍 / 后续可做

1. **占两份磁盘**：这是「复制」的必然代价。曲库位置目前固定在 `%APPDATA%`（系统盘）；
   后续可在设置里加「曲库位置」并做迁移（注意：Track id 按路径哈希，换位置需同步迁移 id）。
2. **老条目不会自动迁移**：已导入的外部路径曲目继续可播，不做批量复制（避免升级瞬间
   大量拷贝）。需要的话可以后续加一个「整理曲库」动作。
3. **单个大文件复制无进度**：进度是按文件推进的，复制一个超大视频时会停在当前文件。
